# Rust/WASM + Canvas SDK 性能复测

本批保留 Rust 布局、Canvas2D 默认渲染和 WebGL2 可选渲染。TableView 首次创建时，普通标量行共用列名表，只传行键和按列排列的值。嵌套值、自定义 JSON 序列化和列回调仍使用原有格式。固定尺寸场景的空根帧推迟到首个子控件可一起参与布局时。读取同步快照或显式调用 `render()` 仍会立即取得布局结果。

每个窗口的离屏场景主画布共用 8 MiB 保留预算，回到视口时从原控件树重新绘制。Canvas2D 对空闲合成、向量、字形和光栅缓存分别计量。WebGL2 对缓存纹理按 RGBA 像素计量，对合成池另外计算深度/模板缓冲。关闭浮层时释放浮层及背景采样像素。预算约束 SDK 可控制的保留资源，活动帧允许使用完成原分辨率绘制所需的临时表面。

## 对照方法

- 独立表格使用 npm tarball、Vite 生产构建、10,000 行、4 列、DPR 1.5，同样滚动 5,120 px。分别记录挂载时间、首屏最长主线程任务和滚动后工作集。
- 独立 React 压测使用 28 个不同数据源的重型页面、5 页缓存、DPR 1.5。分别读取末页、返回首页和清空缓存后的主渲染进程工作集。
- Gallery 使用 Chrome 有头模式、1440 × 1000、DPR 2.5，两轮共 44 次导航。工作集来自 Windows 进程计数器，报告中的峰值是采样峰值。浏览器内存转储单独记录共享图像、传输缓存和 Skia 的分配口径。

原始报告和复现日志在 `out/sdk-canvas-budget/`。运行脚本分别为 `tools/benchmark-table-renderers.mjs`、`tools/benchmark-sdk-heavy-pages.mjs` 和 `tools/benchmark-gallery-gpu.mjs`。

## 已测得的变化

- 独立表格的初始化数据从 1,040,902 降至 700,902 个字符，样本使用 ASCII，传输字节同样减少约 33%。空场景的同步帧从首挂载路径移除。首屏剩余布局和光栅仍占主要时间。
- 首个生产候选包的两组 Gallery 对照中，GPU 工作集采样峰值分别从 1,170 降到 972 MiB、从 1,120 降到 893 MiB。页面 Canvas RGBA 像素估算峰值从 169–172 降到 92 MiB。Gallery 主渲染进程峰值仍为 443–453 MiB。
- 第一组导航结束回首页时，Chromium 转储的 GPU 共享图像分配从约 289 降到 230 MiB，传输缓存从约 46 降到 41 MiB。共享资源可能在多个进程账目中出现，应分开阅读，不能与 Windows 工作集直接相加。

TableView 的比较同时保留首屏分段计时和 Long Tasks API 数据。场景构造耗时下降只能说明同步初始化减少，整表解析、首次有效布局和绘制仍须计入挂载结果。独立应用返回首页时的工作集和 Gallery 遍历峰值分别报告。

### 交付包复测

使用 `delivery/winui-wasm-0.1.1.tgz` 重新运行三套压力测试。字形预算改为增量计数，合成池在字节预算内保留可复用表面。此构建包含压测期间工作区内独立推进的 ComboBox 等改动，整包结果包含这些差异。

| 指标 | 交付包 |
| --- | ---: |
| 独立表格，场景构造中位数 | 12 ms |
| 独立表格，首屏挂载中位数 | 328 ms |
| 独立表格，首屏最长任务中位数 | 190 ms |
| 独立表格，滚动后主渲染进程工作集中位数 | 172 MiB |
| 独立重页，末页 / 返回首页 / 清空缓存后 | 336–338 / 301 / 277 MiB |
| Gallery，GPU 工作集采样峰值 | 1,012 MiB |
| Gallery，主渲染进程工作集采样峰值 | 494 MiB |
| Gallery，页面 Canvas RGBA 像素估算峰值 | 101 MiB |

独立表格缩短了同步场景构造，首个有效帧仍花费约 63–85 ms 做 Rust 布局。端到端首屏和长任务未达到优化目标。Gallery 本轮 GPU 峰值低于 1 GiB，余量约 12 MiB，主渲染进程未接近 300 MiB。原始报告为 `table-delivery.json`、`heavy-delivery.json`、`gallery-delivery.json` 和 `gallery-delivery-dumps.json`。
